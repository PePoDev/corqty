# Milestone 4: organization secrets and worker leak prevention

## Contract

The secret API exposes metadata only. Admins create, replace and delete values; editors
can list names for graph references. Runners and viewers cannot list secrets. Secret
IDs remain stable across replacement, and future attempts read the current encrypted
version. Secret values are UTF-8 strings of 1–65,536 bytes, excluding NUL; names have
1–100 characters after trimming.

- `GET /api/v1/orgs/{org}/secrets` → `{items:[{id,name,createdAt,updatedAt}]}`.
- `POST /api/v1/orgs/{org}/secrets {name,value}` → 201 and metadata.
- `PUT /api/v1/orgs/{org}/secrets/{id} {name,value}` → metadata.
- `DELETE /api/v1/orgs/{org}/secrets/{id}` → 204, or 409 `secret_in_use`.

No GET-by-ID or plaintext-retrieval operation exists. Name conflicts return 409.
Cross-organization identifiers return 404. All writes and administrative audit events
share one tenant transaction.

## Encryption

`CORQTY_MASTER_KEY` is mandatory in API and worker binaries, apart from the worker's
read-only healthcheck subcommand. It is standard base64 encoding of exactly 32 random
bytes. Tests inject a deterministic key directly instead of mutating environment state.

HKDF-SHA256 derives an organization key using the domain-separated salt
`corqty.secret.encryption.v1` and the organization UUID as expansion information.
AES-256-GCM encrypts each value with a fresh OS-generated 96-bit nonce. Authenticated
data binds organization UUID, object UUID and key version. Ciphertext records carry
key version 1; unsupported versions fail closed. The master key is never persisted.
The same envelope supports encrypted webhook signing secrets, with the trigger UUID
as object identity. Master keys and redactor values are zeroized on drop, and Debug
implementations never expose key or decrypted context values.

## Database boundary and deletion

Migration `202611040001_secrets.sql` gives the API column-level SELECT access only to
secret metadata. RLS enforces tenant membership for metadata and admin privileges for
mutations. The worker role retains no table privileges.

The sole new worker function, `corqty.bound_secrets(worker,node,fence)`, acquires the
existing lease lock, verifies the lease has not expired, and returns ciphertext only
for explicit references in that node's pinned graph. Config secret-reference widgets
and input bindings are recognized. Foreign organization references return nothing.
Retrieval writes `secret.used` with node-run identity and attempt, never plaintext.

Deletion is blocked by references in any current draft or immutable published version.
Enabled triggers pin published versions, so those references are protected transitively.
Graph writes, secret availability checks and deletion share a transaction-scoped
organization advisory lock, closing publish/delete and draft-save/delete races.

Publishing, blueprint creation and node-definition defaults validate against a locked
snapshot of available secret IDs and enabled, approved runtime identities. Availability
is checked inside domain validation before diagnostic limits are applied. This avoids
rejecting valid graphs with more than 200 secret/runtime references, and still checks
the final node for malformed or foreign references.

## Worker execution

Workers decrypt after acquiring a job, resolve and validate secret-bound inputs in
memory, then replace those input values with opaque `{kind:"secret",secretId}` references
before invoking runtime components. Runtime plaintext access remains gated by the
host's `secret-read` capability. Trusted compiled executors receive the resolved input.
The execution context contains only secrets explicitly bound to that attempt.

Persisted input views, log text and executor errors pass through an exact-value redactor.
Log prefixes that might be partial secrets remain buffered across chunk and periodic
flush boundaries independently for stdout/stderr/system. Full secret matches are
replaced longest first. Outputs are inspected recursively, including object keys and
scalar values; an exact bound-secret value fails the attempt with non-retryable
`secret_output_detected`, and no output is persisted or released downstream.

Detection is not an exfiltration boundary: encoded or transformed values and fragments
cannot be guaranteed detectable. This limitation is displayed in the secrets UI.

Runtime preparation renews the lease and obeys cancellation, shutdown and the node
deadline while the Wasmtime host compiles a component. Its duration counts against the
same node timeout as execution.

## Verification

- Domain tests cover fresh nonces, authentication of tenant/object/key version,
  tampering, invalid master keys, nested redaction, and every UTF-8 split/flush boundary.
- API tests cover metadata-only CRUD, encryption at rest, nonce replacement, safe audit,
  fixed roles, cross-tenant requests, draft/published deletion guards, secret-reference
  defaults and publishing a 260-node graph with valid secret bindings.
- Resource-validation regressions cover 300 runtime nodes with input and config secrets,
  300 secret defaults, and errors beyond the diagnostic threshold's original position.
- Persistence tests cover exact fenced ciphertext access, unrelated and foreign secret
  exclusion, revoked leases, and denied API/worker ciphertext table reads.
- Worker tests cover plaintext resolution, per-job secret isolation, split logs across
  actual periodic flushes, persisted input redaction, secret-output failure, and errors.

Commands and actual results are recorded in the final launch verification report; tests
must pass with the complete runtime-plugin and automation integration before release.
